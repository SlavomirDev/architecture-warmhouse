# WarmHouse

# Задание 1. Анализ и планирование

### 1. Описание функциональности монолитного приложения

Текущий монолит на Go выполняет две основные функции:

**1. Управление отоплением**

У пользователей есть возможность управлять системой отопления и мониторить температуру в своих домах.

А также система даёт возможность:
  - Добавлять нове объекты с использованием специалиста 
  - Настройку и регулировку климат-контроля 
  - Телеметрию данных о температуре: сбор и передачу

**2. Мониторинг температуры:**

Есть возможность получать инорфмацию о температуре дома
А через систему есть возможность:
  - Получения необходимой информации о температуре
  - Добавление новых датчиков, но с использованием специалиста

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует полной остановки всего приложения.

Для целевой экосистемы нам нужно абстрагироваться от конкретного типа устройства и создать гибкую систему.

### 3. Определение доменов и границы контекстов

- Домен Управление устройствами/датчиками.
    - Контекст датчиков
- Домен Мониторинг.
    - Контекст температуры/отопления.

### 4. Проблемы монолитного решения

Можно выделить следующие проблемы монолитного решения:
  - Проблема масштабируемости
  - Проблема скорости разработки и развертывания
	- Из-за единой кодовой базы нескольким разработчикам придётся работать над одним большим проектом, из-за чего высок риск конфликтов в коде.
	- Медленный деплой из-за необходимости производить деплой всего монолита
  - Проблема Надежности (Отказоустойчивости)
	- Баг в малоиспользуемом модуле может привести к падению всего приложения

# Задание 4. Создание и документирование API

## 1. Тип API
### REST API для синхронного взаимодействия "запрос-ответ":

Обоснования:
- Для взаимодействие API с микросервисами (Identity, Devices, Billing).
- Стандартно, просто, хорошо понимается разработчиками, идеально подходит для HTTP-запросов от клиентов.

### Асинхронная коммуникация через брокер сообщений для событий:

Обоснования:
- Для уведомлений о событиях.
- Развязывает сервисы, повышает отказоустойчивость и позволяет обрабатывать события в своем темпе.

Считаю, что гибридный подход (REST + Messaging) — это наиболее эффективный способ построения отказоустойчивых микросервисных архитектур.
